## Problem
A developer who needs a second branch checked out at the same time has two bad options: stash and switch (risky, loses their place) or a second clone (wasted disk, drifts). `git worktree` solves it, but GitHydra can only show a branch as "checked out elsewhere"; it cannot create, open or remove a worktree.

## Target user
A working developer on any repo (local, GitHub, GitLab, Bitbucket, self-hosted, bare, submodules, worktrees) who reviews a PR mid-feature, fixes a hotfix beside a long task, or runs agents in parallel. Many do not know the word "worktree"; the create dialog says: "A second folder with another branch checked out, sharing this repo's history. No second clone."

## Product rules this spec must not break
No account, no telemetry, no network, no backend. git via argv arrays only. GitHydra itself never runs a script. Nothing is deleted or copied that the user has not seen named. Nothing is written into the user's repo except by git itself.

## A. git-core (`packages/git-core`; git-core-engineer)
- **FR-601 listWorktrees.** Typed entries: `id` (the admin-dir name; `null` for the main worktree), path, branch or detached short SHA (`branch: null`), `isMain`, `isBare`, `locked` (+ reason), `prunable` (+ reason), HEAD sha, `supported` (false for an entry whose path cannot be represented or trusted), and a list-level `untrusted` flag. Parse `git worktree list --porcelain -z` when git is 2.36 or newer; on older gits (the supported floor is 2.24; git 2.31 on the owner's machine rejects `-z`: "unknown switch `z`") do NOT trust the newline format on its own, because a crafted `<common-dir>/worktrees/<id>/gitdir` containing an interior newline can forge `HEAD` and `worktree <path>` lines using only recognised keywords (an "any unrecognised line" rule never fires). Instead list entries from `<common-dir>/worktrees/*/gitdir` (the id is the directory name) and use `git worktree list --porcelain` only to cross-check. An entry is `supported: false` (listed, never openable, never removable) if its `gitdir` file has any CR or LF other than one trailing terminator. The porcelain output must contain exactly one block per admin directory plus the main block, in strict order `worktree`, `HEAD`, then `branch`/`detached`/`bare`, then optional `locked`/`prunable`, with no duplicate keys; any mismatch marks the whole list `untrusted` and disables Open and Remove for every linked entry. If any admin record names a UNC or device path, or on Windows any path that is not drive-letter absolute (`\??\UNC\...`, a single leading backslash; a mapped drive letter that points at a share cannot be detected by string and is a stated limit), `git worktree list` is not run at all, including by the Branches panel's own listing (branches then carry `worktreeInfoUnavailable` and the UI offers no worktree actions) (git itself would stat the network path, an NTLM leak): the list is rebuilt from the admin directories with the reason `network-path`, those entries are `supported: false` and Create refuses (`listUntrusted`). Lock reasons are always read from the `locked` file (the newline porcelain quotes them); an entry whose text decodes lossily (U+FFFD) is `supported: false`. Prunable and lock-reason detail on gits too old to print them is read-only derived from `<common-dir>/worktrees/<id>/{gitdir,locked}`; git-core-engineer verifies the exact git versions of each porcelain field before build. "Missing" and "prunable" come from git's output, never from a GitHydra filesystem probe. Dirty state (changed-file count) is computed on demand for ONE entry (the remove confirm), never polled and never shown on rows. The private parser in `branches.ts` moves here and is shared; `branches.ts` behaviour (FR-33, FR-42) is unchanged. No Node globals at module load (`rendererSafeLoad`).
- **FR-602 addWorktree.** Exactly one of: existing free branch; new branch name + start commit; detached at a commit; remote-only branch (creates a local tracking branch named after the remote branch, from the named remote, no network). Never `--force`. Refuses with a typed reason and NO side effects (no folder, no branch, nothing in `.git/worktrees`) when: the branch is checked out in another worktree (reason names its path), the destination fails FR-639, the branch name fails `git check-ref-format --branch`, or the name is taken. Further typed refusals: `hookChanged`, `hookFingerprintRequired`, `hooksPathRelative` (FR-644), `configHooks` (config-defined hooks cannot be disabled by `core.hooksPath`, so Create is refused on a git new enough to honour them, gate `CONFIG_HOOKS_MIN_VERSION`, unverified on the owner's 2.31) and `listUntrusted` (FR-601). A timeout (a consented hook is the likely cause) is handled like a post-creation failure: if the worktree appeared it is kept and reported `createdButFailed`, otherwise it is rolled back with a typed `timeout`; raw filesystem errors map to `io-failed`. Works from a bare repo. A failure after git created the worktree (for example a failing filter) reports "created, but <reason>" and keeps the worktree. Rollback on mid-flight failure removes only what this call created.
- **FR-603 removeWorktree.** `git worktree remove <path>` run with cwd = the main worktree (or the common dir), never inside the target, without `--force` by default. Typed refusals, never raw stderr: `dirty` (count), `locked` (reason), `hasSubmodules`, `inUse` (a Windows busy-folder failure: "Close programs using this folder and try again"; leaves no half state), `main`, `unsupported`. Dirty count = tracked changes + untracked files, each untracked directory counted by its files (`git status --porcelain=v1 -z -uall`). A second explicit `force` exists only for `dirty` and for `hasSubmodules` (after the confirm lists the submodules that have uncommitted changes, checked with git); never for `locked` or `main`; `--force` is never doubled (a second `--force` is how git removes a locked worktree). A target inside the main workdir under which main tracks files is refused `unsafeTarget`. A FORCED removal is bound to the dirty count and submodule list the user confirmed (`expectedCount`, `expectedSubmodules`): if the fresh state differs it is refused with the fresh numbers (the UI says "This worktree changed since you opened this. Review it again." and re-opens the confirm; it never retries the force) and force is not honoured; force without an expectation is refused (`expectationRequired`). On Windows, untracked links and junctions inside the worktree are unlinked first (git for Windows 2.31 follows junctions when deleting and deleted files outside the worktree); tracked symlinks are skipped, but a link at a submodule (gitlink) path is foreign and IS unlinked; because that changes what git sees, the dirty/submodule decision is repeated after the pre-step; a walk failure is the distinct refusal `walkFailed`; refusals report `linksUnlinked`.
- **FR-604 pruneWorktree ("Forget missing worktree").** `git worktree prune` has no per-entry argument and also forgets other missing worktrees (for example on an unplugged drive). Run `git worktree prune --dry-run --verbose` first; run the real prune only if exactly the targeted entry would be pruned; otherwise the confirm lists every entry that would also be forgotten ("If a drive is only unplugged, reconnect it instead; `git worktree repair` can recover it") and the user confirms the whole list. After the real prune its `--verbose` output is diffed against the dry run and any extra forgotten entry is reported ("also forgot X"); output is parsed by admin-dir id. Deletes no files.
- **FR-605 Remove and delete branch ordering.** Remove the worktree first; only after success run `git branch -d` (never `-D`). If the branch is unmerged the delete is skipped and reported; the worktree stays removed. The merged/unmerged decision shown when the dialog opens is re-checked at delete time; if the outcome differs the banner reports what actually happened.
- **FR-606 Self-write and refresh.** GitHydra's own add/remove/prune use the self-write refresh gate (`specs/self-write-refresh-suppression.md`) and raise no external-change alert. An add/remove/prune made in a terminal is picked up because git-core's watcher also watches `<common-dir>/worktrees` (that directory only, non-recursive) and the list also refreshes on window focus; the existing live-refresh constants are used (no new timers). Un-awaited refresh calls use `refreshRefsAndRowsInBackground()` (CLAUDE.md pitfall).
- **FR-638 Git invocation safety.** Every new call goes through the existing `gitProcess` seam: cached absolute git path, `safeEnv()` (already sets `GIT_LITERAL_PATHSPECS=1`, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`). `worktree add` runs with `-c core.fsmonitor=false -c core.hooksPath=<private empty dir>` (the helper `partialStaging.ts` uses, not `/dev/null`), so, unless the user has allowed the hook for this repository (FR-644), neither a planted `post-checkout` hook nor a planted `core.fsmonitor` can run when the user clicks Create (Improvement over plain git, which runs hooks without asking; the per-repo choice to run the hook is FR-644; the existing switch/checkout `post-checkout` exposure is roadmap). This does NOT make Create code-free: repo-local filter drivers (`filter.*.smudge` / `process`) selected by `.gitattributes`, textconv and similar still run during the checkout inside `worktree add` (the same trust class as switch/checkout, recorded in `ROADMAP.md`); never claim that no repo code can run on Create. The sentinel tests cover hooks and fsmonitor and document the filter case as a known gap. git-lfs keeps working (LFS uses filters; only its `post-checkout` lock-flag hook is disabled). Output that is parsed is produced with `LC_ALL=C` (git's strings are localised). `update-ref -d` and `branch -d` also run with the empty hooks directory (`reference-transaction` fires on them), and clean filters also run during `status` (the dirty count) and `worktree remove`'s own check, not only on Create. `list`, `remove` and `prune` run with `-c core.fsmonitor=false`. No `--force` (except the allow-listed force remove), no `-D`, no `--no-verify`. Paths go to git as absolute paths after an option terminator. `safe.directory` is never set. IPC errors carry typed reasons with redacted paths, no raw stderr, no `-c` values.
- **FR-639 Destination validation (in git-core, not in the dialog).** Refuse, with a specific reason: a leaf that is a symlink or junction; a path whose existing ancestors' realpath chain is unstable; a path inside the repo working tree, inside `.git` or the common dir, inside any registered worktree, or that is an ancestor of the repo or of any worktree; a UNC path (`\\server`, `\\?\UNC`) or a drive root or the home directory; a path longer than 260 characters on Windows (measured after realpath expansion of 8.3 names); `\\.\` device paths and forward-slash UNC (`//server/share`) count as UNC; a non-empty existing folder; a folder that already is a worktree (names its branch). Windows folder-name hygiene applies on every platform to the default slug and the leaf: characters `< > : " | ? * \` become `-`, trailing dots and spaces are trimmed, reserved names (`CON`, `NUL`, `COM1`..., also with an extension) get a `_` prefix, an empty slug becomes `worktree`, a collision with an existing sibling gets `-2`. Other drives are allowed; git's own refusals (for example "dubious ownership") surface as typed reasons.
- **FR-640 Worktree metadata is untrusted.** `.git/worktrees/<id>/gitdir` is repo-controlled, so a hostile repo can list a worktree at any folder. Before a worktree is opened as a tab, dirty-counted or handed to an editor, in this order: (1) reject UNC, `\\?\`, `\\.\`, `//host` and reserved-device leaf names by string, without touching the filesystem; (2) `lstat` `<path>/.git` and require a regular file; (3) read it (capped at 4 KB) and require exactly `gitdir: <p>`; (4) realpath `<p>` and require it to equal `<common-dir>/worktrees/<id>` for that id (git's own back-link check, done without spawning git inside an untrusted folder); then, as a second check only, `git -C <path> rev-parse --git-common-dir` with `-c core.fsmonitor=false`. The path is never `stat`ed before step 1. A registered worktree that lies INSIDE the main workdir (for example `.worktrees/x`, or Claude Code's `.claude/worktrees/*`) is allowed when steps 1 to 4 pass: the back-link check is the control, being nested adds no risk (a forged worktree can fake the back-link either way), and refusing it would make the user's own existing worktrees unopenable (changed 2026-10-13 after slice 1 shipped the stricter rule; creating a NEW worktree inside the repo stays refused by FR-639). Otherwise show "Not a worktree of this repository" and do nothing. GitHydra never stats or realpaths a UNC or network path taken from metadata. Git's own check (the target's `.git` file must point back at the admin dir) remains the defence for `git worktree remove` and must not be bypassed.
- **FR-641 Remove IPC authority.** The renderer sends a worktree id (the admin-dir name), not a path. The main process re-runs the list and compares the path the user confirmed; refuse if: the target is a symlink or junction; it is the main worktree (whether the path is canonical or an alias that realpaths to it); it is the main workdir, the common dir, an ancestor of either, a drive root or the home directory; it contains another registered worktree.
- **FR-644 Hook trust (owner decision 2026-10-13: "like git, with an explanation").** `git worktree add` runs `post-checkout`, and plain git also fires `reference-transaction` (git 2.28 and later, on branch creation) and `post-index-change`; the dialog lists those other hook names too (`otherHooks`). Detect it read-only: the effective hooks directory (`core.hooksPath` if set, else `<common-dir>/hooks`) holds a regular, non-sample `post-checkout` file. Only then, on the first Create for that repository (and again whenever the hook set changes), show a dialog (the ConfirmDialog shell, Cancel as initial focus) in plain words: "This repository has a post-checkout hook: a program stored in the repository that git runs automatically after a checkout. It can run any code. Run it only if you trust this repository." It shows the hook's path and its first lines read-only (capped), the buttons "Run hook" and "Skip hook", and a checkbox "Remember my choice for this repository" (off by default). "Run hook" creates the worktree with `core.hooksPath` pointing at a private directory holding only a re-hashed copy of that one `post-checkout` (so no other hook fires; a hook that finds sibling files through `$0` sees the private directory; fsmonitor stays neutralised); "Skip hook" creates it with the empty-directory override. git-core requires `expectedHookFingerprint` with "Run hook" and re-reads the hook right before the spawn (`hookChanged` if it differs). A relative `core.hooksPath` (it resolves inside the NEW worktree at run time) cannot be consented to (`hooksPathRelative`) and the dialog never offers "Remember" for it. A remembered choice is per repository and bound to a fingerprint (the hook path, the full-file sha256, the executable bit, the `core.hooksPath` value and the sorted names of every non-`.sample` file in the hooks directory): any change asks again. The dialog preview shows invisible and right-to-left characters as visible escapes and says when it was truncated. There is NO global "never ask again" switch. Choices live in a main-process file under `userData`, NOT in renderer storage (a renderer compromise must not be able to mark a repo trusted), keyed by the argument-less sha256 repo key (`specs/worktree-copy-ignored.md` FR-629). No hook present: no dialog. Repo-local filter drivers still run regardless (FR-638). A small mockup of this dialog is made before the UI slice. **Dialog requirements from the slice-1 security review:** the UI passes the fingerprint returned by git-core and never constructs one; it handles `hookChanged`, `hookFingerprintRequired`, `hooksPathRelative` and `configHooks`; it shows the hook path, the `core.hooksPath` value, the size and line count, "N more lines not shown" when `previewTruncated` and "this file is not text" when `previewIsBinary` (NUL bytes or mostly replacement characters in the head); it says the hook runs from a private copy (a hook that finds siblings through `$0`, or a temp folder mounted `noexec`, can fail) and that the other hooks listed in `otherHooks` stay disabled; "Run hook" is never the default; a remembered choice is keyed on the fingerprint; the app calls `sweepStaleConsentDirs()` at startup. Known upstream gap, recorded in git-core's README: the Branches panel's own worktree listing is made safe for network-path records (slice 1), but other automatic git paths that may enumerate or prune worktrees (`gc --auto`, checkout/switch/branch -d) have not been checked for statting a planted network gitdir.

## B. Create (ui-graphics; Improvement over GitKraken: a prefilled dialog with an editable folder, because GitKraken's fixed folder is a known complaint on its feedback board)
- **FR-607 Entry points: exactly ONE worktree item per menu.** Branch menu: **Create worktree...** when the branch has no worktree and is not checked out anywhere; otherwise **Open worktree** (the accordion of `specs/external-programs.md` FR-617) with "Checked out at <path>" as its secondary text. Never both, never a disabled twin. Commit menu: **Open worktree** when a worktree has this commit as its HEAD; otherwise **Create worktree from commit <sha>...** (a second worktree from a commit that already has one is reachable from the palette). A remote-only branch shows **Create worktree...** and creates a local tracking branch named after it, from that remote. Palette: "Worktree: Create new branch in a new worktree" (starts from HEAD; the current branch can never get a second worktree), "Worktree: Create from branch..." (branch picker; checked-out branches listed disabled, with the reason reachable by keyboard), "Worktree: Open..." and "Worktree: Remove..." (list pickers over the registered worktrees; the main and locked entries are listed disabled with their reasons; Open uses the same default program/GitHydra-tab accordion of `specs/external-programs.md`).
- **FR-608 Create dialog.** Standard shell (440 px wide, Enter confirms, Esc cancels), sticky footer, fits a 800 px HIGH window with only the body scrolling. Top line: the one-sentence definition. Fields: read-only source chip (branch) or "New branch name" input (commit, with "Detached HEAD (no branch)" under Advanced and an inline warning that new commits can be lost); Folder prefilled with the default (FR-609) with Browse and a wrapped absolute-path preview (a "Will create:" line only when the path is relative or edited); "Open after create" (default on); Advanced (collapsed) holding detached HEAD and the copy line of `specs/worktree-copy-ignored.md`. A relative path is resolved against the repo parent and the resolved path shown, then validated by FR-639. Validation messages appear in the field (the input has `aria-describedby`; no toast): folder not empty, inside the repo, a worktree already at that folder (names its branch, with an "Open" link), branch already checked out (names the path, with an "Open that worktree" link), branch-name errors reuse `NewBranchDialog`'s messages verbatim.
- **FR-609 Default folder.** `<main-repo-parent>/<main-repo-name>.worktrees/<branch-slug>`: `<main-repo-*>` derives from the MAIN worktree (or the bare repo's name with `.git` stripped), never from the linked worktree the user is looking at; slashes in the branch name become `-` and the FR-639 hygiene applies. Never inside the repo. Editable per create; no global setting in v1.
- **FR-610 Focus.** Focus lands on Folder when the branch is fixed, on the branch-name input for a commit; Enter in any field creates; the primary button is "Create worktree".

## C. Open, tabs, left panel
- **FR-611 Open in GitHydra opens a NEW tab** (Improvement over GitKraken's replace-current-tab default). Tab identity is the realpath of the worktree top-level: a linked worktree already open as a plain repo tab counts as open; if open, focus that tab instead of opening a duplicate (a toast "Already open" is allowed, not asserted). The main worktree maps to the repo's own tab. The bare repo's own entry is not a worktree and is not openable. Double-click or Enter on a Worktrees row does the same. FR-640 applies before opening.
- **FR-612 Tab label.** Branch name first, in primary ink; the repo name is shown (muted, as a suffix) only when more than one repo is open; a detached worktree reads "detached <short sha>". The house glyph marks the main worktree only when the repo has two or more worktrees; the worktree glyph marks every linked worktree tab. Long names truncate in the middle by character count in JS (maximum 24 characters with NO CSS width cap, so the JS cut is what shows and two branches sharing a prefix stay distinguishable; e.g. "feature/PROJ-1...debounce-v3"), not by CSS. The label does not change meaning when a second tab opens. Full path in the tooltip and `aria-label`. All names render as text nodes with control and bidi characters made visible.
- **FR-613 Worktrees list (left panel, v1 scope).** A plain "Worktrees" section: one row per worktree with glyph, branch or detached sha, a "tab" flag when open as a tab, the flags Locked and Missing (icon + word, one style), and the full path as selectable secondary text AND as a hover tooltip. Row actions: Enter or double-click opens as a tab; right-click, the "..." button, Shift+F10 or the menu key opens the row menu (Open worktree, Copy path, Remove, Remove and delete branch, Forget missing worktree). A Branches-panel card for a branch that has a worktree shows the worktree glyph in the footprint of today's "Checked out elsewhere" pill, with the path in its tooltip and `aria-label`. In the roadmap epic (not v1): glyphs on graph ref chips (they compete with the `+N` popover, FR-411), the dirty dot, per-worktree "// WIP" rows in the graph, and the rest of the left-panel work. Row anatomy (after the Impeccable critique): two lines, hairline-separated; line 1 is glyph, name, flags and the "..." button; line 2 is the path middle-cut keeping the leaf, with the full path in the tooltip and `aria-label` and a "Copy path" row-menu item; roving focus (one Tab stop for the list, arrows move); the list is capped at about five rows with its own scroll; Missing is styled more serious than Locked; branch cards show "In worktree" next to the glyph; the collapsed section carries a one-line hint.
- **FR-614 Locked and missing states.** Locked: Remove is disabled with "Locked: <reason>. Unlock it with git worktree unlock before removing." (no Unlock button in v1; lock/unlock buttons are roadmap). Missing (git says prunable): Open is disabled with "Its folder is missing." and the menu offers **Forget missing worktree**: "Its folder is missing. Forgetting it removes the leftover Git record. No files are deleted." (FR-604 confirm applies).

## D. Remove
- **FR-615 Menu and confirms.** Row menu: Open worktree, **Remove this worktree**, **Remove worktree and delete branch** (separate item). Clean worktree: confirm with Cancel as initial focus and "This also deletes ignored files such as node_modules and build output in <path>." (clean is not harmless: git ignores those). Dirty: the confirm states the file count; above 20 files the user must type the count, exactly like `BulkDiscardDialog` (Cancel initial focus, Enter in the typed field never confirms, label "Type N to confirm (more than 20 files)"; exactly 20 needs no typing, 21 does; one shared threshold constant). `hasSubmodules`: the confirm lists the submodules with uncommitted changes before offering force. Remove-and-delete-branch decides from merge state when the dialog opens: merged keeps "Remove worktree and delete branch" / "Remove and delete branch"; unmerged downgrades to "Remove worktree" with "Branch X has N commits that are not merged into <current branch> or its upstream, so it will be kept." (N is the real count, or "some commits" if not computed). The path appears once. After confirming, focus moves to the Worktrees heading.
- **FR-616 Open tab interaction.** If the worktree is open as a tab: the confirm says the tab will be closed first; a non-active tab is activated first and then closed through the dirty-leave guard (`registry.guard`); an unsaved editor buffer stops the removal and nothing is deleted; GitHydra's own watchers on that folder are stopped before `git worktree remove` runs.
- **Outcome notices** (in-flow banners, persistent until dismissed, at the top of the Branches panel): unmerged: "Worktree removed. The branch X was kept because it has commits that are not merged into <current branch> or its upstream. Delete it anyway from the Branches panel if you are sure." with "Open Branches" and Dismiss; merged: "Worktree and branch removed."

## G. After create, feedback, cross-cutting
- **FR-632 Submodules.** If the new worktree has submodules (`.gitmodules`), an in-flow banner offers "Initialize submodules", run only on click: `git submodule update --init` (NOT `--recursive` in v1: nested `.gitmodules` URLs are unknown before the click) with `-c protocol.ext.allow=never -c protocol.fd.allow=never -c core.fsmonitor=false -c core.hooksPath=<private empty dir>` and `GIT_ALLOW_PROTOCOL=https:http:ssh:git` (never `protocol.file.allow=always`). It shows the submodule hosts before the click (credential helpers send credentials to those hosts), classified by one parser: scheme URL, scp-like `[user@]host:path` (no `/` before the first `:`), relative (`./`, `../`, shown as "same host as origin"), or other; userinfo is stripped, host and port are shown, percent-decoded, IDN hosts in punycode; any URL beginning with `-`, containing CR/LF/NUL or control characters, or using `ext::`, `fd::`, `file:` or a local path is shown as "blocked" and disables the whole button; progress and Cancel (the whole process tree is killed on Windows). It is disabled with an explanation and a "Copy command" fallback when git is older than the patched floor of its maintenance track for the known submodule vulnerabilities (CVE-2024-32002, CVE-2025-48384 and earlier ones). The gate is a unit-tested constant table keyed by maintenance track (parse major.minor.patch, ignore vendor suffixes such as `.windows.1`); the security-reviewer's recollection is 2.45.1 with the 2.39 to 2.44 backports for the first and 2.50.1 with the 2.43 to 2.49 backports for the second, and the table MUST be verified against upstream advisories and git-for-windows release notes at build; and when a `.gitmodules` path contains CR/LF, `..`, `.git` or a symlinked component. On the owner's git 2.31 the button is therefore disabled; that is intended (owner decision 2026-10-13), with a banner: "Your git is 2.31.1. Update git to enable this button; until then copy the command."
- **FR-633 Dependencies.** When a manifest is present (`package.json` + a lockfile, `pyproject.toml`, `Cargo.toml`, `go.mod`, `Gemfile`, `composer.json`), a reminder banner: "package.json found - dependencies are not installed in this worktree." with "Copy command" putting a fixed string from a built-in table on the clipboard (never anything derived from repo content). GitHydra never runs it.
- **FR-634 Feedback layer.** Outcomes are in-flow banners at the top of the affected panel (the create result above the Worktrees list, or above the Branches panel when the list is collapsed): icon + light status tint + plain 1px border, NO side stripe, text-safe ink tokens (the app-wide banner look of `specs/banner-uniform-look.md`, FR-645..648, which lands before this slice; worktree banners reuse the shared banner classes and add no styling of their own), persistent until dismissed when they carry an action or an outcome. Floating toasts only for tiny non-actionable confirmations ("Opened in VS Code", "Already open", "Copied"). Create result: `Created worktree "feature-x". Copied 3 files (4 KB) from acme.` and the other variants of `specs/worktree-copy-ignored.md`. The notice never mentions remembering. The follow-ups after a create (dependency reminder FR-633, submodules FR-632, hook skipped FR-644) are ONE grouped banner with one quiet Dismiss, each a short line with its own quiet action (the `gh-status-banner__action--quiet` modifier); the create dialog reuses the shared NewBranchDialog shell and always shows the resolved path.
- **FR-635 Keyboard and accessibility.** Everything is keyboard-complete with visible focus; menus return focus to the invoking control on Esc; disabled reasons are reachable; interactive targets have a border box of at least 24x24 CSS px (glyphs may stay smaller); meaningful text is at least 12 px; meaningful muted text meets 4.5:1 once the proposed `--gh-ink-muted-text` token lands (Open question 6).
- **FR-636 Icons.** New `Icon.tsx` components (18x18 grid, `currentColor`, 2 px stroke, `aria-hidden`, always paired with text or an `aria-label`); no raster, no emoji, no Unicode glyph standing in for an icon.
- **FR-637 Principles.** No request to a non-`file:`/`devtools:` URL from the renderer or main session during the whole flow (counted in the e2e); no telemetry; no account; no backend.

## Acceptance criteria
git-core (GC = git-core vitest with a real fixture repo; fixtures create the repo inside a unique temp parent so the sibling `.worktrees` folder is cleaned)
1. Creating from a free branch makes the folder at the default sibling path and `git worktree list` shows it; also from a bare repo, a repo whose path has spaces, a non-ASCII branch (`feature/日本-é`), and when the source is itself a linked worktree (default folder still derived from the main repo name).
2. The runner spy records every argv of every public function on success and failure paths: none contains `--force`, `-f` or `-D`, except the single allow-listed call in `removeWorktree({force:true})` for a `dirty`/`hasSubmodules` target; a source grep over `packages/git-core/src/worktrees*.ts` finds `--force`/`-f`/`-D` only there; every pathspec-bearing call carries `--literal-pathspecs` via `safeEnv`.
3. From a commit with a new branch name: branch and worktree both exist. Detached: git-core returns `branch: null` and a 7+ character head; the Worktrees row and tab render "detached <short sha>".
4. After any refusal (non-empty target, inside the repo, existing worktree, branch checked out, bad name, symlink leaf, UNC), `git worktree list --porcelain`, `git for-each-ref` and the `snapshotTree` of the repo and its parent directory are identical to before; a read-only parent directory (POSIX CI only) leaves no new branch.
5. Removal: clean removes the folder and keeps the branch; dirty is refused with the file count (untracked directories counted by files); an ignored-only worktree is removed and its ignored files deleted (data-loss path); locked is refused with its reason and `force` on locked is refused; `hasSubmodules` is its own typed reason; the main worktree is refused whether the given path is canonical or an alias (trailing slash, differing case on Windows, `..`, 8.3 short name); a symlink/junction target is refused; removal runs with cwd outside the target; a worktree containing a junction (Windows) or symlink (POSIX) to an outside directory holding a file: after removal the outside file survives.
6. Remove-and-delete-branch: the worktree is removed first; an unmerged branch is kept (`git branch -d` refuses, argv never contains `-D`) and the result says so; if worktree removal fails `git branch -d` is never called.
7. Clean up runs `prune --dry-run --verbose` first; with two prunable entries, cleaning up A when B would also be pruned asks for confirmation listing B and removes nothing until confirmed; no file is deleted.
8. Self-write and refresh (renderer vitest with fake timers): a GitHydra add/remove/prune leaves `hasExternalChanges` false and raises no alert; a worktree added by an external process appears after one refresh via the `<common-dir>/worktrees` watcher or window focus, using the existing constants and a fake clock; one real-Electron smoke polls with a 10 s cap and is non-gating.
9. FR-638: with a planted `post-checkout` hook and a planted `core.fsmonitor` in the source repo, `worktree add` leaves no sentinel file from either (unless the user chose "Run hook" for that repo, AC 21); list/remove/prune neutralise fsmonitor.
10. FR-601 on git without `-z` (run for real on this machine's git 2.31 and version-stubbed elsewhere): entries come from the admin directories; a forged `gitdir` containing `\nHEAD <sha>\n\nworktree /evil` yields exactly one `supported: false` entry and NO `/evil` row; porcelain output that does not match the admin directories block for block marks the list `untrusted` and disables Open and Remove for linked entries.
11. FR-639/640/641: each refusal case has a fixture; a forged `.git/worktrees/<id>/gitdir` pointing at an unrelated folder is shown as "Not a worktree of this repository" and cannot be opened, dirty-counted or removed.
