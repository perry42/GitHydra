# PRD: Stash

Status: draft — next in v1 build order after merge/rebase + conflict resolution (`PRODUCT.md`, `CLAUDE.md`)
Owner: product-manager
Priority: P0 — fifth feature in the v1 build order, immediately after merge/rebase + conflict resolution (shipped)

Builds on `packages/git-core`'s existing working-directory (`workingDirStatus.ts`), diff (`diff.ts`), and conflict (`conflicts.ts`) modules, and on `packages/desktop`'s `ChangesPanel`/`BranchesPanel`/`ConflictResolutionView`/`StatusBanner` component language (`DESIGN.md`). Also extends two decisions already on record before this spec existed: `specs/self-write-refresh-suppression.md` FR-6b explicitly names "future merge/rebase/cherry-pick/**stash** mutations" as needing the same in-flight self-write-suppression gate — this spec is that follow-through, not new ground; and `specs/merge-rebase-conflict-resolution.md`'s conflict classification/diff/accept-side/mark-resolved primitives (`conflicts.ts`) are written generically off index stages, not off `MERGE_HEAD`, which is exactly what makes them reusable here (see "A sharp edge" below).

**Sequencing:** git-core-engineer builds first (a new `stash.ts` module plus the two watcher/self-write-suppression touch points below); ui-graphics builds second, against those return shapes, wiring a new `StashPanel`, a `CreateStashDialog`, a new `"stashes"` value on `App.tsx`'s `RightPanel` union, and the reused `ConflictResolutionView`.

**Scope decision (user-confirmed 2026-09-01):** `git stash branch` deferred as a fast-follow, not pulled into this v1 pass. Rest of PM's scope confirmed as-is, including no confirmation dialog on Apply/Pop and reusing the merge conflict UI with no abort affordance for stash conflicts.

## Problem

A developer who needs to set aside uncommitted work — to switch branches cleanly, pull in an update, or just get a messy working tree out of the way temporarily — has no way to do it from GitHydra today; every stash create/list/apply/pop/drop requires dropping to a terminal. Stash is the fifth-most-frequent git workflow in `PRODUCT.md`'s v1 priority order, immediately after merge/rebase, and today the app has no concept of it at all — `getWorkingDirectoryChanges()` shows staged/unstaged/untracked/conflicted, but "temporarily shelve this and come back to it later" isn't representable.

Stash also carries git's own well-known sharp edges for a GUI to get right: apply vs. pop is a real, consequential distinction most GUI users have never had explained to them; stash apply/pop can conflict exactly like a merge, but — critically — does **not** produce an in-progress-operation state (no `MERGE_HEAD`, no `--continue`/`--abort`), so a client that only knows how to handle merge-style conflicts will either mishandle this or silently do nothing. Getting this wrong either hides real, consequential choices from a git-literate user or (worse) implies an "abort" affordance that doesn't correspond to anything git can actually do.

## Target user

Same as every prior spec: a developer working day-to-day against local-only, GitHub/GitLab/Bitbucket/self-hosted, or no-remote repos — including bare repos (no working tree, so stash is entirely inapplicable), worktrees (stash's ref list is shared across all worktrees of a repo even though apply/pop act on whichever worktree is current — a real, non-obvious git behavior this spec must get right), detached HEAD, a zero-commit/unborn-HEAD repo (stash requires at least one commit to exist), and a stash created, applied, or dropped from a terminal outside GitHydra, which must show up/disappear correctly without restarting the app. Per `PRODUCT.md`'s "Users" description, this target user already knows git and does not need "apply" and "pop" explained from scratch — they need the distinction visible and correctly labeled, not hidden or dumbed down.

## Must-have behavior

### Data & git semantics (git-core-engineer) — new `packages/git-core/src/stash.ts`

- FR-81: `listStashes()` — every entry from `git stash list`, parsed for: its index (`stash@{N}`), full message (git's default `WIP on <branch>: <sha> <subject>` or a custom message verbatim), the branch it was created on (parsed from the default message, or `null` for a custom message / detached-HEAD creation), the creation date, and the parent commit SHA it was created against. Read fresh from disk on every call — no cached/authoritative in-memory copy, same convention `branches.ts`/`conflicts.ts` already establish. Returns `[]` (not an error) when there are no stashes, and returns `null` on a bare repository (no working tree, matching `getWorkingDirectoryChanges()`'s existing bare-repo convention).
- FR-82: **Stash list scope is the common git dir, not the per-worktree gitDir.** Unlike `MERGE_HEAD`/rebase state (per-worktree), `.git/refs/stash` and its reflog live in the repository's common git directory and are visible from every linked worktree. `listStashes()` must read from the common dir so a stash created in one worktree's tab is visible (once refreshed) in every other tab open on a different worktree of the same repository — do not scope this the way `detectInProgressOperation` correctly scopes `MERGE_HEAD`.
- FR-83: `getStashDiff(stashIndex)` — the full set of files the stash would change if applied, including any untracked files it captured (when created with `--include-untracked`), with diff content per file reusing `diff.ts`'s existing binary/too-large guard pattern and its established "diff a merge-like commit against its first parent" convention (a stash entry is internally a commit with the pre-stash `HEAD` as its first parent). Read-only — never touches the working tree or index.
- FR-84: `createStash(options)` — `git stash push`, supporting: an optional custom message (`-m`, piped the same stdin-safe way `createCommit()` handles messages — never string-concatenated), an explicit list of paths to stash (`-- <pathspec>...`, file-level only — see Non-goals) defaulting to "every eligible changed path" when omitted, and an `includeUntracked` flag (`--include-untracked`). Conflicted paths are never included in the eligible set, mirroring `stageAllFiles()`'s existing "never touch conflicted paths" rule. Refuses with a specific typed error (not a raw git error) when there is nothing eligible to stash, or when `HEAD` is unborn (no commits yet — `git stash` cannot create a stash commit with no parent).
- FR-85: `applyStash(stashIndex)` (`git stash apply stash@{N}`) and `popStash(stashIndex)` (`git stash pop stash@{N}`) as distinct, separately-named exports (mirroring FR-40/FR-41's create/force-delete separation) — never inferred from one call with a flag, so the UI cannot reach the destructive-adjacent "remove from list" behavior by accident. Both surface git's real exit state: success (clean apply), conflict (files left unmerged — see FR-86), and refusal (e.g. local changes would be overwritten) with git's actual reason, never swallowed or generic.
- FR-86: **Conflicts on apply/pop reuse `conflicts.ts`'s existing per-file primitives, not a new conflict system — but do not synthesize a fake in-progress-operation.** `git stash apply`/`pop` produce conflicts via an internal merge but create no `MERGE_HEAD`/`rebase-merge` state — `detectInProgressOperation()` correctly returns `null` afterward, and this module must not fabricate one. What conflict resolution needs is already generic: `getWorkingDirectoryChanges().conflicted`, `classifyStageCombination`, `getConflictFileDiff`, `scanConflictMarkers`, `acceptConflictSide`, and `markConflictResolved` are all already sourced from live index-stage state, not from operation-type detection — they work unmodified against a stash-apply conflict. Confirm this directly (a stash-apply conflict's stage-2/stage-3 blobs resolve the same way a merge's do) and add regression coverage; do not add new "ours"/"theirs" logic for this case.
- FR-87: **Matching git's own real behavior, exactly:** `popStash()` only removes the stash entry when the apply step succeeds cleanly. On conflict, `popStash()` behaves identically to `applyStash()` — the stash entry remains in `git stash list` — and the conflicted files are left in the working tree/index for the user to resolve. There is no `git stash pop --abort`; do not build one (see "A sharp edge" below and Non-goals).
- FR-88: `dropStash(stashIndex)` (`git stash drop stash@{N}`) — a separately-named, explicit destructive export (matching FR-41's isolation pattern), never reachable via apply/pop's code path.
- FR-89: All of FR-84–FR-88 that touch the working tree or index (`createStash`, `applyStash`, `popStash`) route through `withFsmonitorNeutralized()`, exactly as every other working-tree-mutating call in this module already does (`gitProcess.ts`); `dropStash()` (ref-only, no working-tree touch) does not need it, matching `git branch`'s precedent in `branches.ts`.
- FR-90: All calls use argv arrays only, `shell: false`; any user-supplied message or path goes through the same stdin/`--end-of-options`/literal-pathspec conventions the rest of the module already enforces. None of FR-81–FR-88 make a network call, and all behave identically regardless of remote host or absence of one.
- FR-91: **Watcher coverage.** `watchRepositoryRefs()` (`watcher.ts`) is extended to also watch the common-gitDir's `refs/stash` ref file and its reflog directory (parent-directory watch, same "watch the containing directory to catch not-yet-existing file creation" technique FR-59 already established for `MERGE_HEAD`) so a stash created/dropped from a separate terminal while GitHydra is open triggers the existing external-change alert path.
- FR-92: **Self-write suppression.** Per `specs/self-write-refresh-suppression.md` FR-6b (which already names stash mutations as in scope), `createStash`/`applyStash`/`popStash`/`dropStash` calls issued from GitHydra's own UI must never surface the "History changed outside GitHydra" banner as a side effect of their own write — the renderer gates the in-flight window exactly as it already does for branch switch/checkout, refreshing directly from each call's own result rather than waiting on the watcher.

### Rendering & interaction (ui-graphics) — `packages/desktop`

- FR-93: A new `"stashes"` value is added to `App.tsx`'s `RightPanel` union (alongside `"none"`/`"commit"`/`"changes"`/`"branches"`), following the exact pattern `"branches"` established (a `Toolbar` toggle button, `githydra:layout:rightPanel` persistence per `specs/layout-and-view-polish.md`, mutually-exclusive with the other toggleable panels). The toggle carries a live stash count badge (`git stash list`'s length), refreshed on every mutation and on the FR-91 watcher/FR-92 self-write paths.
- FR-94: A `StashPanel` (new; ui-graphics's call on exact chrome, consistent with `DESIGN.md`) lists every stash from FR-81 in `stash@{0}`-first order, each row showing: its message, the branch it was created on (or a "(detached HEAD)" caption when none is resolvable), a relative/absolute date, and Apply/Pop/Drop controls. Given it needs a file-list+diff split (unlike the single-list `BranchesPanel`), it follows `ChangesPanel`/`DetailPanel`'s two-region layout convention and 680px/`80vw`-capped default width, resizable via the existing `ResizeHandle`/`useResizableWidth` pattern, not `BranchesPanel`'s narrower single-list treatment.
- FR-95: Selecting a stash row shows its FR-83 diff (file list + `DiffView`) in the panel's diff column — read-only, no stage/unstage controls, matching how `DetailPanel` shows a historical commit's diff rather than `ChangesPanel`'s editable file rows.
- FR-96: **Apply and Pop are both always shown, as separate, clearly labeled buttons — never merged into one control or hidden behind a menu.** Per `PRODUCT.md`'s target user (already git-literate), the buttons read "Apply" / "Pop," not dumbed-down paraphrases, with a `title` tooltip on each spelling out the concrete effect — reusing `BranchesPanel`'s established "ahead/behind last-known" tooltip-caption pattern rather than inline prose: Apply's tooltip reads "Apply this stash's changes, keep it in the list"; Pop's reads "Apply this stash's changes and remove it from the list." Neither routes through `ConfirmDialog` — applying/popping does not discard anything the user doesn't already have (its content becomes working-tree changes; on conflict, per FR-87, the stash is retained regardless), so this is not a "No Single-Click Destruction Rule" case.
- FR-97: Drop **does** route through `ConfirmDialog` (`destructive: true`, naming the stash's message), per the No Single-Click Destruction Rule — dropping is the one stash action that discards content that exists nowhere else.
- FR-98: **Stash-apply/pop conflicts open the existing `ConflictResolutionView`** (same component `ChangesPanel`'s Conflicted rows already open) — no new conflict UI is built. But the surrounding chrome is deliberately different from the merge/rebase case: no operation banner, no Continue/Abort. Instead, on a conflicting apply/pop, show a distinct, non-blocking notice (e.g. inline in `ChangesPanel`'s Conflicted section header, or a one-line banner scoped to that state) reading to the effect of "Applying stash left conflicts to resolve — the stash was not removed from the list" (worded per whether Apply or Pop was invoked), pointing at the newly-populated Conflicted section. The existing Accept Ours/Accept Theirs/Mark as Resolved controls (FR-86) are used as-is.
- FR-99: A "New Stash…" action opens a `CreateStashDialog` (reusing `ConfirmDialog`'s modal shell as a form, matching `NewBranchDialog`'s precedent): an optional single-line message field (empty = git's own default message), a checklist of every currently staged/unstaged/untracked changed file (reusing `FileStatusIcon` + path rendering from `ChangesPanel`'s file rows) defaulting to **all checked**, and an "Include untracked files" checkbox defaulting **unchecked** (matches git's own default — least surprising to a git-literate user, and avoids silently sweeping build output that happens not to be gitignored). Conflicted paths are never listed as selectable (matches FR-84). The action is reachable both from `StashPanel`'s header (primary entry point, matching `BranchesPanel`'s "+ New Branch" placement) and from `ChangesPanel` (secondary convenience entry point, since that's where the user is already looking at the changes they might want to shelve) — exact chrome for the second entry point is ui-graphics's call.
- FR-100: The create action is disabled (with a `title` reason) when there is nothing eligible to stash (clean working tree, or every changed path is conflicted) or when `HEAD` is unborn — never a submit that produces an empty stash or a crash.
- FR-101: After any successful create/apply/pop/drop: refresh the Toolbar's stash-count badge, `StashPanel`'s list, `ChangesPanel`'s file sections and working-dir-status badges, and the graph's uncommitted-changes pseudo-node — no restart required, same standard `FR-56`/`FR-30`-style "refresh everywhere" contract every prior mutating spec has set, and per FR-92 never by way of the watcher/stale-banner path for the app's own action.
- FR-102: Every ahead/behind-style "last known" caveat this spec introduces (the branch-created-on caption, FR-94) is text, never color-only, consistent with the status-token policy already in force everywhere else in `DESIGN.md`.

### Edge cases & constraints

Bare repo (no working tree — the Toolbar's stash toggle and every stash action render disabled with an explicit "no working directory" reason, matching `ChangesPanel`'s existing bare-repo state, rather than `listStashes()` even being called; per FR-81 it returns `null` and the UI treats that the same way `getWorkingDirectoryChanges() === null` is already handled today); unborn HEAD / zero-commit repo (create disabled per FR-100, list/apply/pop/drop are moot since no stash could ever have been created against this repo's current history — though a stash created before the repo somehow lost its only commit is not a real-world case worth guarding beyond FR-84's typed refusal); detached HEAD (stash creation works normally; the row's branch caption reads "(detached HEAD)" instead of a name, matching `BranchesPanel`'s existing "no branch as current" convention); worktrees (FR-82's shared-list, per-worktree-effect behavior — a stash listed from worktree A's tab can be applied from worktree B's tab and will affect only B's working tree/index); a stash created, applied, or dropped from a separate terminal (FR-91's watcher coverage triggers the existing external-change alert — never silently reflected, consistent with every other "external change" case in the app); applying a stash on a different branch than the one recorded in its message (works with no special gate or warning dialog — the branch caption, FR-94, gives the user the context to decide, consistent with `PRODUCT.md`'s "legibility over configuration" principle rather than adding friction); a submodule's recorded commit pointer changing as part of a stashed/applied file set is treated like any other file — no new submodule-specific stash handling is built (the existing gitlink-conflict treatment from `merge-rebase-conflict-resolution.md` already covers the conflict case if one occurs).

### A sharp edge worth stating plainly

Stash apply/pop conflicts are **not** an in-progress operation the way merge/rebase/cherry-pick/revert are. Git resolves them via an internal merge but writes no `MERGE_HEAD`-equivalent state, and there is no `git stash apply --abort`. This spec deliberately does **not** invent one: on a conflicting apply/pop, the user's recovery path is the same per-file tools already shipped (`ChangesPanel`'s Discard, or hand-resolving via `ConflictResolutionView`) — never a synthesized "undo this stash apply" action, which would either be a no-op wrapper around existing discard actions or, if implemented as a broader `git reset --hard`, a genuinely more destructive operation than anything git itself offers for this case.

## Non-goals (v1)

- **Hunk-level partial stash.** File-level selection only (FR-84/FR-99), matching the same file-level-not-hunk-level precedent `stage-unstage-diff.md` set for staging and `merge-rebase-conflict-resolution.md` set for conflict resolution.
- **`git stash branch <name>` (create-and-switch-to a new branch seeded from a stash).** A real, useful git capability, but a materially separate flow (branch creation + apply, composed) — deferred as a fast-follow, not dropped, once this spec's plumbing exists. (User-confirmed 2026-09-01.)
- **`--all` (including ignored files) when creating a stash.** Only `--include-untracked` is exposed (FR-99); including ignored files (build output, etc.) is a rarer, riskier default to expose in a checkbox a user might toggle without reading closely. A terminal remains available for that rare case.
- **A synthesized "abort" for a conflicting apply/pop.** See "A sharp edge" above — existing per-file Discard/resolve tools already cover recovery; no new destructive superstructure is built to imply a git capability that doesn't exist.
- **Editing/renaming a stash's message after creation.** Not a clean git primitive (there's no `stash reword`); permanently out of scope, not merely deferred.
- **`git stash clear` (drop every stash at once).** No bulk-destroy affordance — drop is always one stash at a time through FR-97's confirmation, avoiding a high-blast-radius action for marginal convenience.
- **Auto-stash-around a branch switch, pull, or any other convenience layering.** `branch-management.md` already excluded auto-stash-and-pop around a switch for the same reason: it would blur two separate, separately-prioritized features. Unchanged here.
- **Any network call** as part of list/create/preview/apply/pop/drop — none, per product principles; identical behavior with or without a configured remote, regardless of host.
- **Recursing into a submodule's own repository** for a stash that touches a submodule pointer — same boundary `merge-rebase-conflict-resolution.md` already drew.
- **Telemetry on stash usage, frequency, or apply/pop choice.** None, by default.

## Acceptance criteria

1. Creating a stash with every eligible file selected and no custom message produces a new `git stash list` entry with git's own default message, and `git status --porcelain` is empty immediately afterward.
2. Creating a stash with only a subset of changed files selected leaves every unselected file's changes untouched in the working tree/index afterward, and `git stash show -- <path>` on the created stash touches only the selected paths.
3. Creating a stash with "Include untracked files" checked captures untracked files (verified via `git stash show -u`); leaving it unchecked leaves untracked files exactly as they were (still untracked, unaffected by the stash).
4. Supplying a custom message results in that exact string (not git's default "WIP on...") shown by `git stash list`.
5. With a clean working tree, or a working tree where every changed path is conflicted, the create action is disabled with a stated reason and produces no stash entry if attempted.
6. On a zero-commit (unborn HEAD) repository, stash creation is disabled with an explicit message rather than crashing or erroring against a raw git failure.
7. The Stash panel lists every entry from `git stash list`, in the same order, including one created from a separate terminal after GitHydra was already open (visible once the FR-91 watcher/external-change alert is acknowledged or the panel is reopened).
8. Selecting a stash entry shows a diff of every file it would change (including any captured untracked files) without altering `git status --porcelain` at any point before or after the preview.
9. Apply on a cleanly-applicable stash applies its changes and leaves the entry present in `git stash list` afterward.
10. Pop on a cleanly-applicable stash applies its changes and removes exactly that entry from `git stash list` afterward (list length decreases by one, all other entries' indices/content otherwise unaffected).
11. Apply or Pop that produces a conflict: leaves the stash entry present in `git stash list` in both cases (matching git's real pop-never-drops-on-conflict behavior), populates `ChangesPanel`'s Conflicted section with the affected files, shows the FR-98 stash-specific conflict notice, and shows **no** merge/rebase operation banner and no Continue/Abort controls.
12. Accept Ours / Accept Theirs / Mark as Resolved on a stash-apply conflict behave identically to the equivalent actions on a merge conflict, including refusing to resolve a file that still contains a literal conflict-marker line (FR-66's existing marker-scan gate, reused unmodified).
13. Drop always opens `ConfirmDialog` first; canceling leaves every stash untouched; confirming removes exactly the targeted `stash@{N}` (verified via `git stash list`) without altering any other stash or the working tree/index.
14. Applying a stash while on a different branch than the one named in its own message succeeds with no gate or warning dialog, and the panel's caption correctly names the stash's original branch throughout.
15. On a bare repository, every stash-related control (Toolbar toggle, panel, create/apply/pop/drop) is disabled with an explicit "no working directory" reason rather than erroring when interacted with.
16. In a repo with two linked worktrees, a stash created via worktree A's tab appears in worktree B's tab's Stash panel once B is refreshed/reactivated; applying that stash from B's tab affects only B's working tree/index, leaving A's untouched.
17. Zero outbound network requests occur across a full create → list → preview → apply/pop → drop flow, on repos configured against GitHub, GitLab, Bitbucket, a self-hosted remote, and a purely local repo with no remote — identical behavior in every case.
18. None of create/apply/pop/drop ever show the "History changed outside GitHydra" staleness banner as a result of their own action, verified across 5+ consecutive stash operations in one session; a stash created or removed from a separate terminal while GitHydra is open and idle still triggers the ordinary external-change alert, unchanged.
19. After any successful apply or pop, `ChangesPanel`'s file sections, the Toolbar's working-dir-status indicator, the graph's uncommitted-changes pseudo-node, and the Stash panel's own list/badge count all reflect the result with no restart or manual refresh required.
