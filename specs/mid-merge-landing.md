# Mid-merge landing

Opening a repo that is in the middle of a merge, rebase or cherry-pick with conflicts should feel like "we are in the middle of merging", not like a one-line hint. Design approved from `mid-merge-landing-mockup.html` state S2; the drawer, conflicts-first list and block editor are unchanged (specs/conflict-first-layout.md, specs/edit-in-diff.md).

- **FR-577 (conflict banner):** While conflicts remain, the operation banner is a labelled region (`aria-label` "Merge in progress" etc.) with a warning icon, a bold headline from `operationBanner.ts` ("Merge in progress: feature into main", "Rebase in progress: x onto y" plus a "Step N of M" chip, "Cherry-pick in progress: abc1234 "subject" (N more queued)"), a muted "N files have conflicts", segmented progress with "R/T resolved", a primary filled **Resolve conflicts (N)**, Continue disabled with the reason as tooltip and accessible description, and an outlined Abort. Resolve conflicts opens Changes on the first conflict through `dirtyGuard.guard`. The text block is a polite live region.
- **FR-578 (resolved state):** At 0 conflicts, after at least one was seen this operation, the banner turns calm green: "All conflicts resolved — merge ready", no Resolve button, primary **Continue merge** (rebase, cherry-pick likewise) using the same single Continue handler as before. With no conflict ever seen it makes no "all resolved" claim.
- **FR-579 (working-directory row):** With an operation in progress and conflicts, the dashed Uncommitted row is the conflict state: orange dashed frame, warning icon in the ref gutter, then right of the lane art "Merge in progress · N conflicts" with the other counts secondary. Truncation priority is the other counts, then the label (full text in `title`/`aria-label`); the conflict count never truncates. The icon, text and lane art (node ring and dashed connector) sit in disjoint columns at any gutter width, so nothing overlaps. Click or Enter opens Changes. Fixes the cherry-pick label/connector collision and "1…" truncation.
- **FR-580 (auto-open):** When a repo opens or a tab activates with conflicts in an operation, Changes opens on the first conflict, once per tab per operation (key: kind + merge head / rebase step+onto / picked commit). Never again after the user closed it, never while an unsaved-edit guard is active, always via `dirtyGuard.guard`. Evaluated once per open sequence, after the tab switch has settled and the working-directory status has loaded.
- **FR-581 (reduced motion):** The banner and row add no animation.
- **FR-582 (tab and title):** The active repo tab shows a warning badge with the conflict count (icon + number, tooltip "N conflicts to resolve", tab name includes it). The window title is "repo — Merging (N conflicts)" (Rebasing, Cherry-picking, else Resolving) and returns to "GitHydra" when resolved. Assumption: only the active tab's count is known (one live graph), so background tabs show no badge.
- **FR-583 (command):** Palette entry "Resolve conflicts" (disabled with a reason when there are none). "Next conflict" and "Next conflicted file" already exist (FR-572).

Tokens: `--gh-serious-ink`, `--gh-good-ink`, `--gh-critical-ink` (text-safe variants of the fixed status colours) added to `theme.css`.
