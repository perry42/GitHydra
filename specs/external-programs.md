# Open in an external program (editor picker, Programs dialog)

Status: BUILT, not merged (branch feat/external-programs and the branches above it; security-reviewed with its changes applied; macOS and Linux detection and launch are tested only against fake layouts; see Review log; the owner can overrule). Split out of the worktrees spec on review (2026-10-13). Reviewed by security-reviewer, product-manager and test-agent; second security pass on the revised text pending (see "Review log"). Owner: product-manager. Companion of `specs/worktrees.md` (the "Open worktree" menu item) and independently useful on ANY repo, including ones with no worktrees. Owns FR-617..625 and FR-642. Extends `specs/keyboard-shortcuts-command-palette.md` (FR-223). Default stance: GitKraken has no external-program picker, so this is a GitHydra addition; the closest comparisons are the editor launch in GitHub Desktop (a detected-editor dropdown plus "Configure Custom Editor") and Fork's "Open in".

Visual truth: the approved clickable mockup (`worktree-mockup/index.html`, scratchpad) after the Impeccable fixes. This text wins over the mockup.

## Problem
Opening the current repo or a worktree folder in the user's own editor is a daily need that GitHydra does not cover. Editors live in different places on every OS, and some are not on the PATH.

## Target user
A developer who uses VS Code, Cursor, a JetBrains IDE, Sublime, Notepad++, Zed or similar, on Windows, macOS or Linux, who does not want to configure anything and who may use an editor GitHydra has never heard of.

## Product rules this spec must not break
No network, no account, no telemetry. argv arrays only, never a shell string. GitHydra never executes anything found during detection. A custom program is a user trust decision recorded locally only.

## E. Behavior
- **FR-617 The "Open worktree" accordion.** Inside the existing flat `ContextMenu` (no cascading submenu; a menu chain is not a GitHydra pattern) one row "Open worktree" with a secondary line. Click on the row body runs the default; the chevron or the Right arrow expands an indented list in place: **GitHydra tab**, then each detected editor (the default carries a check and "default"), then a disabled row for a program that is not found (disabled children stay focusable: `aria-disabled` + `aria-describedby` pointing at the reason), then **Manage programs...**. Left collapses and returns focus to the parent; Esc closes the menu and returns focus to the invoking control. Opens collapsed (`aria-expanded="false"`, children out of the accessibility tree). First run with no default: the click expands instead of launching. The parent has `aria-haspopup="menu"`, `aria-expanded`, and the hint "Opens in <program>" is also in its accessible description (`aria-description` is not announced by every screen reader, so the text lives in an `aria-describedby` element too): "Enter opens in <program>, Right arrow chooses another program". Focus lands on the default child on expand. Default = last used (one stored value; no separate pinned default in v1); choosing a non-default program says "Opened in Cursor. Cursor is now your default." If the default disappears, fall back to GitHydra tab and say why.
- **FR-618 Detection, Windows.** Read the Uninstall registry hives (HKCU, HKLM, WOW6432Node) with `%SystemRoot%\System32\reg.exe query` via argv (no shell, no native module, absolute path so a planted `reg.exe` in the cwd or PATH cannot win). Match DisplayName prefix AND Publisher, then take the editor's **InstallLocation joined to a known per-editor executable basename** (`Code.exe`, `Cursor.exe`, `sublime_text.exe`, ...), never `DisplayIcon` verbatim (it often points at the uninstaller). The file must exist and end in `.exe`; a mismatch is "not found". For HKCU hits the install directory must be under `%LOCALAPPDATA%\Programs`, `%ProgramFiles%` or the JetBrains Toolbox directory (registry data is writable by any of the user's own processes); `%SystemRoot%` is validated as a drive-absolute path; `reg.exe` and `mdfind` run with the same scrubbed env as launches. JetBrains Toolbox entries and the current and previous JetBrains IDE versions are included. Not PATH-based. Reference editor lists: GitHub Desktop's open-source detection lists (VS Code and Insiders, VSCodium, Cursor, Windsurf, Zed, Sublime, Notepad++, the JetBrains IDEs, Pulsar, Brackets, Typora, others). GitHydra builds its OWN list from the facts (registry keys, bundle ids, paths) and credits the source; run the `oss-licensing-guardrails` skill before copying anything verbatim.
- **FR-619 Detection and launch, macOS.** Look apps up by bundle identifier (from the built-in list only) with `/usr/bin/mdfind "kMDItemCFBundleIdentifier == '<id>'"` via argv. Realpath every `mdfind` hit and accept only hits under `/Applications`, `/System/Applications` or `~/Applications` that are not inside any repo or worktree (a hostile repo can ship an `Evil.app` with a legitimate bundle id and Spotlight indexes it); launch with `/usr/bin/open -a <that absolute .app path> <folder>`, never `-b` (LaunchServices could pick a planted copy); never a bare `open <folder>` (a folder named `Evil.app` would launch) and never `--args`. Not dependent on the `code` shell command being on PATH.
- **FR-620 Detection, Linux.** Check the known executable locations (`/usr/bin`, `/snap/bin`, flatpak export folders for system and user, JetBrains Toolbox scripts) AND search the directories on PATH for known command names (`code`, `codium`, `subl`, `zed`, `idea`, ...). Only absolute PATH entries are used; `.`, empty and relative entries are ignored; every hit is realpath'd and shown in the Programs dialog; a hit inside an open repo, a worktree or a world-writable directory is ignored; known-location results are preferred over PATH results. AppImages are not detected ("Add your own" covers them).
- **FR-621 Detection safety.** Runs on demand and is cached; "Rescan" is in the Programs dialog. Never throws: no editors installed yields an empty list plus "Add your own". Detected entries are re-validated with a stat when the menu opens (cache lifetime: until the next Rescan or app start). Nothing is executed during detection; no network. The spawn re-checks the file is a regular file (an accepted check-to-spawn window).
- **FR-622 Launch.** `spawn(exe, [folder], { shell: false, detached: true, stdio: 'ignore', cwd: <home directory>, env: <scrubbed> })`. The env drops every `ELECTRON_*`, `NODE_*` and `GIT_*` variable (`ELECTRON_RUN_AS_NODE` would also break Electron-based editors) plus `LD_PRELOAD`, `DYLD_*`, `PYTHON*` and `_JAVA_OPTIONS`. Never the repo or worktree as cwd. The exe is absolute, not inside any repo or worktree, and on Windows a real `.exe` (extension and `MZ` magic); `.cmd`, `.bat`, `.ps1`, `.lnk`, `.vbs` are refused at save time (Node cannot spawn `.cmd`/`.bat` without a shell since the CVE-2024-27980 fix, and a shell would reopen injection through `&`, `%`, `^` in the folder name); detection resolves editors to their `.exe`. The folder is a realpath'd, absolute path that equals a registered worktree or the root of an open repo tab (FR-640 of `specs/worktrees.md`), never a UNC or `\\?\UNC` path (touching one triggers SMB/NTLM). With an absolute realpath a leading `-` is impossible; any argv entry that starts with `-` after resolution is rejected. A folder with spaces, `&`, `;`, `$()` or quotes arrives intact as one argument. A spawn failure shows an inline banner naming the program and path; nothing is retried. No free-text arguments field in v1.
- **FR-642 Program records and IPC authority.** Program records (name, absolute exe, default id, hidden ids) live in a main-process file under `userData`, NOT in renderer storage (a renderer compromise must not be able to register `C:\x\evil.exe`). Add and Locate paths come only from a main-side `dialog.showOpenDialog`. The launch IPC takes `{programId, worktreeId or repoId}`, never an exe or folder string; main resolves both. Errors carry typed reasons with redacted paths. **Exe rules, re-run at every launch (not only at save):** the exe's realpath ancestors are walked for a `.git` entry; an auto-detected hit inside a repo, a worktree or a world-writable directory is ignored, while a HAND-ADDED exe in such a place needs a confirm showing the full path (not a hard refusal: a user may keep tools under a repo-rooted projects folder); system interpreters (`cmd`, `powershell`, `pwsh`, `wscript`, `cscript`, `mshta`, `rundll32`, `regsvr32`, `bash`, `sh`) are refused at save time, because they would treat the folder argument as command text.
- **FR-623 Programs dialog.** Built on the `IdentityProfilesDialog` shell as a self-contained component so it can move into a future Settings page. Rows: name, path, Default radio, Hide/Show, Locate... for a missing program, Remove for hand-added ones. Buttons: Add program... (main-side file picker; the path must exist, be absolute, be executable and pass FR-622's exe rules) and Rescan. Auto-detected entries can be hidden, not deleted; the default program cannot be hidden. A missing hand-added program stays as a disabled row "Not found at <path>", never silently dropped. No account, no network.
- **FR-624 Open folder in editor.** A split button on the repo tab ("Open folder in editor" + chevron) and the Command Palette use the same list and default on any repo, worktree or not. The folder is the open repo's top level (FR-622 rules apply).
- **FR-625 Palette entries** (`getCommands()` per the CLAUDE.md convention): "Worktree: Open...", "Worktree: Remove..." (both listed in `specs/worktrees.md` too), "Manage external programs", "Open repository in external program". Per-target actions that need a selected branch stay in menus only.

## Non-goals (v1)
Custom arguments or templating; a Settings page (Programs, Identity, default worktree folder); Linux AppImage detection; reorder by drag; launching terminals; remote or WSL paths; opening a specific file at a line.

## Open questions (owner)
1. Clicking the row body launches an external program, while users may expect "Open worktree" to open inside GitHydra. Mitigated by the hint "Opens in <program>" and by the first-run expand; alternatively the body always opens the GitHydra tab and editors live behind the chevron only.
2. Windows `.cmd`-only installs (a tool that ships only `code.cmd`) are not supported; "Add your own" requires a real `.exe`. This is a security decision, not a convenience one: a `.cmd` launch needs a shell, and `%`, `^`, `&` in a folder name become injection. The security review says keep refusing; do not relax it casually.
3. macOS and Linux detection cannot be verified on the owner's Windows machine; logic is tested against fake layouts on any OS, real launches on CI runners or by hand. "Add your own" is the fallback.

## Acceptance criteria
1. (JS) The accordion is one menu row: click launches the default (spawn spy called once with the default exe); chevron/Right expands and moves focus to the default child; Left collapses and returns focus to the parent; Esc closes and returns focus to the invoker (`document.activeElement` identity); opens collapsed; first run with no default expands and does NOT launch; disabled child has `aria-disabled="true"`, is reachable by arrow keys and its `aria-describedby` resolves to the reason; the parent has `aria-haspopup="menu"`, `aria-expanded` false then true, and the description text exactly as FR-617.
2. (JS) Choosing a non-default program shows "Opened in Cursor. Cursor is now your default."; a vanished default falls back to GitHydra tab with the reason.
3. (JS/GC, pure detectors) Each detector is a pure function of injected `{runCommand, exists, env}`: tests on any OS feed canned `reg query` output, canned `mdfind` output and a temp-dir PATH. Asserts: no editors gives `[]` and does not throw; a rejecting `runCommand` gives `[]`; the argv passed to `runCommand` is an array whose command is the absolute system path of `reg`/`mdfind`; a DisplayName match with the wrong Publisher is excluded; a match whose executable is missing is excluded; a DisplayIcon pointing at an uninstaller is never launched; truncated and non-UTF8 output are tolerated; relative and `.` PATH entries and hits inside a world-writable dir or a repo are ignored; a JetBrains Toolbox entry is found.
4. (JS, spawn seam) The launcher calls the injected `spawnFn` with `(exe, [folder], objectContaining({shell:false, detached:true, stdio:'ignore', cwd: home}))`; `args` has length 1 and `[0]` strictly equals the hostile folder string (spaces, `&`, `;`, `$()`, quotes); the env has no `ELECTRON_RUN_AS_NODE`/`NODE_OPTIONS`/`GIT_*`; a source grep finds no `exec(`, `execSync` or `shell: true` in the launcher and detection modules. One real-process proof on all three OS: spawn `process.execPath` as the "editor" with a small script that writes `process.argv.slice(2)` to a temp file and assert the folder arrived intact.
5. (JS) Save-time rejection with distinct reason strings for: a relative path, a non-existent path, a directory, a non-executable file, a system interpreter (`cmd`, `powershell`, `pwsh`, `bash`, `sh`, ...), and (any OS, string check) `.cmd`/`.bat`/`.ps1`/`.lnk`; a hand-added exe under a repo, worktree or world-writable directory needs a confirm with the full path while an auto-detected one is ignored; the rules re-run at launch; the macOS detector accepts only `mdfind` hits under `/Applications`, `/System/Applications` or `~/Applications` outside any repo and launches with `open -a <absolute .app>`; a program that disappears shows as unavailable when the menu opens (injected `exists`).
6. (main-process unit) Program records are read and written by main only; the launch IPC rejects a payload containing an exe or folder string; a folder that is not a registered worktree or open repo root is refused; a UNC folder is refused.
7. (JS) Programs dialog: Add (via the main-side picker stub), Rescan, Default radio, Hide/Show, default cannot be hidden, Locate for a missing program, Remove only for hand-added entries, a missing hand-added entry stays as a disabled "Not found at <path>" row.
8. (JS) "Open folder in editor" split button works on a repo with no worktrees; palette entries exist with the exact titles and are reachable keyboard-only (one parametrised Playwright test: Ctrl+K, type, Enter, no clicks).
9. (PW) The default persists across relaunch (same `userData`); no request to a non-`file:` URL during the flow.
10. (CI runners) Real detection on each OS asserts only that it never throws and returns an array.

## Security review checklist (security-reviewer, before merge)
1. Program records in a main-process file; add/locate only via main-side dialog; launch IPC by ids.
2. Exe rules, re-run at launch: absolute, ancestor `.git` check (auto-detected hits ignored, hand-added need a confirm), real `.exe` on Windows (extension + `MZ`), `.cmd/.bat/.ps1/.lnk/.vbs` and system interpreters refused, HKCU install dirs constrained, macOS hits constrained to application folders and launched by absolute `.app` path.
3. Folder rules: realpath'd, absolute, registered worktree or open repo root, never UNC; `open -b/-a` only on macOS; neutral cwd; scrubbed env.
4. Detection: InstallLocation + known basename, never DisplayIcon; absolute system paths for `reg`, `mdfind`, `open`; PATH hardening; bundle ids only from the built-in list; nothing executed during detection.
5. No `exec`, no `shell:true`, no network, no telemetry.
