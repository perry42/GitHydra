# PRD: Cherry-pick

Status: draft — sixth feature in the v1 build order (`PRODUCT.md`, `CLAUDE.md`), immediately after stash (shipped)
Owner: product-manager
Priority: P0 — sixth feature in the v1 build order

Builds heavily on infrastructure `specs/merge-rebase-conflict-resolution.md` already shipped generically across every `InProgressOperation` kind, including `"cherry-pick"` by name throughout that spec (FR-58, FR-61, FR-68-71): `RepositoryState.inProgressOperation`/`inProgressOperationDetail` (`packages/git-core/src/repository.ts`, `types.ts`'s `CherryPickOperationDetail`), the operation banner (`StatusBanner`, `operationBanner.ts` — `describeInProgressOperation`'s `"cherry-pick"` case and `OPERATION_LABEL` already exist), generic `abortInProgressOperation`/`continueInProgressOperation` (`conflicts.ts`, already accept `"cherry-pick"` with zero cherry-pick-specific code), the FR-59 watcher coverage of `CHERRY_PICK_HEAD`, and the full conflict-classification/diff/accept-side/mark-resolved/`ConflictResolutionView` stack. This spec's job is narrower than it might look: add the one thing that infrastructure was built to detect but not initiate — actually starting a cherry-pick from the UI — plus the two edge cases neither merge nor rebase has (a multi-commit sequence, and a no-op/empty-result pause).

**Sequencing:** git-core-engineer builds first (a new `cherryPick()`/`skipCherryPickCommit()`/`commitEmptyCherryPick()` surface, a small `CherryPickOperationDetail` extension, and a watcher touch point); ui-graphics builds second, against those return shapes, wiring multi-select onto `CommitGraph`, enabling the existing disabled "Cherry-pick" context-menu stub, and a new empty-result notice alongside the already-shipped `StatusBanner`/`ConflictResolutionView`.

## Problem

A developer routinely needs to pull one or a few specific commits — a hotfix, a commit accidentally made on the wrong branch, a change a release branch needs without a full merge — onto their current branch, without dropping to a terminal. Per `CLAUDE.md`'s v1 priority order this is the sixth-most-frequent workflow, right after stash. Unlike every prior conflict-adjacent spec, GitHydra already has almost all the underlying plumbing: `detectInProgressOperation`, per-operation-kind banner copy, and abort/continue all already treat `"cherry-pick"` as a first-class case, because `merge-rebase-conflict-resolution.md` built that layer generically across every operation kind it named, cherry-pick included. What's missing is the "start one" half — there is no mutating `cherryPick()` call anywhere in `git-core`, the commit graph has no multi-commit selection, and the context menu's "Cherry-pick" item (`CommitGraph.tsx:239`) is a permanently-disabled stub. Two things are also genuinely new here, not covered by the merge/rebase work: a multi-commit cherry-pick is a *sequence* GitHydra initiates, and cherry-pick has an edge case merge/rebase don't — a commit whose changes are already present upstream produces an empty result git itself pauses on, distinct from a real conflict.

## Target user

Same as every prior spec: a developer working day-to-day against local-only, GitHub/GitLab/Bitbucket/self-hosted, or no-remote repos, including worktrees (operation state stays per-worktree, unchanged from FR-76), submodules (a cherry-picked commit touching a submodule pointer is just an ordinary file change here — any resulting conflict already gets the existing gitlink treatment from `merge-rebase-conflict-resolution.md`), detached HEAD (cherry-pick works there with no special gate), bare repos (no working tree — disabled), and — critically, since this spec's whole premise is that GitHydra can now *start* one — a cherry-pick left paused by a terminal, a script, or a teammate's process before GitHydra ever opened the repo, which must be detected and resumable (Continue/Abort) exactly as already required for merge/rebase, even though GitHydra never initiated it and has no memory of what was originally requested.

## Must-have behavior

### Data & git semantics (git-core-engineer) — new `packages/git-core/src/cherryPick.ts`

- FR-103: `cherryPick(shas: string[])` — a single native `git cherry-pick <sha1> <sha2> ... <shaN>` call, in exactly the order given (ordering is the caller's contract to uphold — see FR-114). Using git's own multi-arg sequencer for a multi-commit request, rather than GitHydra issuing one `git cherry-pick` call per commit itself, is a deliberate choice: it's what makes the *existing, unmodified* `abortInProgressOperation`/`continueInProgressOperation` correct for a multi-commit sequence for free — git's native `--abort` restores the pre-sequence HEAD (not just the current step), and native `--continue` auto-advances through the remaining queue. Self-orchestrating single-commit calls instead would silently diverge from that real git behavior (an abort mid-sequence would only undo the current step, leaving earlier picks committed) — precisely the kind of gap `stash.md`'s "sharp edge" section warned against papering over. Refuses up front, with no git call made, via a typed error (mirroring `stash.ts`'s `PreExistingConflictError` precedent) when `detectInProgressOperation()` is already non-null, or when `shas` is empty. Routes through `withFsmonitorNeutralized()`, argv arrays only, `shell: false`.
- FR-104: A clean (non-conflicting, non-empty) `cherryPick()` call returns once git exits 0, with `HEAD` advanced by exactly `shas.length` new commits. A paused outcome (conflict OR the FR-105 empty-result case) is never distinguished in `cherryPick()`'s own return value — matching this codebase's established convention that in-progress-operation state lives on disk and is discovered by re-reading `RepositoryState`/`WorkingDirectoryChanges`, not returned out of band by the call that triggered it.
- FR-105: Extend `CherryPickOperationDetail` with two read-only fields, both sourced fresh from disk every read (never cached): `isEmptyResult: boolean` — true when the paused step's diff is already fully reflected in `HEAD` (`WorkingDirectoryChanges.conflicted` is empty and there is nothing staged that this step needs committed) — the concrete detection mechanism is git-core-engineer's implementation call, verified against real git's actual empty-cherry-pick behavior in tests, not asserted here; and `remainingAfterCurrent: number | null` — the count of still-queued `pick` lines in `.git/sequencer/todo`, `null` when no sequencer state exists (a single-commit cherry-pick, or nothing in progress). See "A sharp edge worth stating plainly" below for why this is `remainingAfterCurrent`, not a `currentStep`/`totalSteps` pair like `RebaseOperationDetail`.
- FR-106: `skipCherryPickCommit()` (`git cherry-pick --skip`) and `commitEmptyCherryPick()` (`git commit --allow-empty`, reusing the paused commit's original message verbatim via the same stdin-safe piping `createCommit()` already uses — never an interactive editor, per FR-70's established precedent) as two new, separately-named exports for the FR-105 empty-result state. Both make no sense to call unless `isEmptyResult` is true; each throws a typed refusal otherwise rather than proceeding to call git blind. After either, git's own sequencer automatically advances to the next queued commit or ends the operation if none remain — no separate "advance" call exists or is needed.
- FR-107: **Regression coverage, not new logic.** `abortInProgressOperation`/`continueInProgressOperation` already accept `"cherry-pick"` generically (`conflicts.ts`) — this spec requires extending their existing test suite with a genuine multi-commit sequence (3+ shas, a conflict on the middle one) verifying `--abort` restores the exact pre-sequence `HEAD` SHA (not merely undoing the paused step) and `--continue` correctly auto-advances through the remaining queue, including pausing again if a later commit also conflicts.
- FR-108: **Watcher: close the same nested-directory gap FR-59 already solved once.** `.git/sequencer/todo` (which backs FR-105's `remainingAfterCurrent`) lives inside a `sequencer/` subdirectory of `gitDir` that is created fresh when a multi-commit cherry-pick starts. The existing non-recursive top-level `gitDir` watch (`watcher.ts`) catches that directory's *creation* but not later rewrites to `todo` inside it as the sequence advances. Add a self-healing nested watch for `gitDir/sequencer/`, mirroring `ensureNestedRebaseWatches()`'s exact technique for `rebase-merge/`/`rebase-apply/`, so `remainingAfterCurrent` stays live when a sequence is advanced from a separate terminal while GitHydra is open.
- FR-109: **Self-write suppression.** `cherryPick`/`skipCherryPickCommit`/`commitEmptyCherryPick` route through the same in-flight suppression gate every other mutating call already does, extending `specs/self-write-refresh-suppression.md` FR-6b's list (which already names cherry-pick as in scope) — none of these ever trigger GitHydra's own "History changed outside GitHydra" banner as a side effect of their own write.
- FR-110: No network call anywhere in this module; identical behavior regardless of remote host (GitHub/GitLab/Bitbucket/self-hosted) or absence of one.

### Rendering & interaction (ui-graphics) — `packages/desktop`

- FR-111: **Multi-select, additive to the existing single-select.** Ctrl/Cmd+click toggles a commit row into/out of a new multi-select set, independent of `selectedSha`/`onSelectCommit` (which continues to drive `DetailPanel` unchanged). Shift+click selects a contiguous range between the last-clicked row and the target, using the currently-rendered graph order. A plain click continues to behave exactly as it does today — single-select, opens `DetailPanel` — and clears any active multi-selection. This spec must not change existing plain-click behavior in any way.
- FR-112: Right-click on a row that's part of a 2+ multi-selection opens a context menu offering **"Cherry-pick N commits"** in place of the single-commit "Cherry-pick" item. Right-click on a row outside the current multi-selection collapses the selection to that single row first (standard list-widget convention) before showing its ordinary single-commit menu.
- FR-113: The single-commit "Cherry-pick" context-menu item (currently a disabled stub, `CommitGraph.tsx:239`) becomes enabled and wired to FR-103. It always targets the currently checked-out branch (`HEAD`) — there is no "pick a target branch" picker; switching branches first (an existing capability) is how a user aims at a different one.
- FR-114: **Application order is derived from graph position, never click order.** For a multi-commit selection, `shas` is sorted into the commits' relative order in the currently-loaded graph, oldest/most-ancestral first, before being passed to FR-103 — regardless of the order the user happened to click them in.
- FR-115: Cherry-pick (single or multi) is shown disabled, with a `title` reason, when: an operation is already in progress (checked client-side before offering the action, mirroring FR-103's server-side refusal, so the menu item's disabled state and the underlying refusal never disagree); the repo is bare or `HEAD` is unborn; or any commit in the current selection is a merge commit (2+ parents — see Non-goals). A merge commit anywhere in a multi-selection disables the whole action rather than silently dropping it from the set — the cherry-picked commits are always exactly what the user selected, never a silently-narrowed subset.
- FR-116: **No `ConfirmDialog` for a clean cherry-pick.** Matches `stash.md` FR-96's precedent exactly: cherry-pick only adds commits, discards nothing, so it is not a No-Single-Click-Destruction-Rule case. Success is communicated by the graph itself — the new commit(s) appear at `HEAD` immediately per FR-121's refresh contract.
- FR-117: A conflicting cherry-pick (single-commit, or any step of a multi-commit sequence) reuses the existing `StatusBanner` (already has cherry-pick-specific copy via `describeInProgressOperation`/`OPERATION_LABEL`) and `ConflictResolutionView` exactly as merge/rebase conflicts do — no new conflict UI is built. For a multi-commit sequence, the banner additionally renders FR-105's `remainingAfterCurrent` (e.g. `Cherry-picking a1b2c3d "Fix off-by-one" (2 more queued)`) instead of a rebase-style "step N of M" — see "A sharp edge" below.
- FR-118: The FR-105 empty-result pause renders a **distinct, non-conflict notice** (not `ConflictResolutionView` — there is nothing to resolve, `conflicted` is empty) naming the specific commit (short SHA + subject) and offering two explicit actions: **"Skip this commit"** (FR-106 skip) and **"Commit anyway (empty)"** (FR-106 allow-empty). Neither is silently auto-applied — both are ordinary, valid git outcomes and the choice is the user's, not a default GitHydra picks for them.
- FR-119: Abort is reachable exactly as it is today (`StatusBanner`'s existing Abort button, behind `ConfirmDialog`, destructive) for a mid-cherry-pick pause of either kind (real conflict or FR-118's empty-result) — no new Abort affordance is built; the existing one already targets `"cherry-pick"` generically.
- FR-120: FR-103's pre-flight refusal and any other cherry-pick failure surface verbatim, in whatever inline error surface the graph's context-menu actions already use — never silently swallowed.
- FR-121: Standard refresh contract, matching FR-56/FR-101's established precedent: after a successful clean cherry-pick, after each Skip/Commit-empty/Continue step, and after Abort — refresh the commit graph (new commits + `HEAD` position), `ChangesPanel`, Toolbar working-dir badges, and the operation banner. No restart or manual refresh required, and per FR-109 never by way of the watcher/stale-banner path for the app's own action.
- FR-122: Every piece of new copy this spec introduces (banner text, the FR-118 empty-result notice, disabled-reason tooltips) is text, never color-only — matches `stash.md` FR-102's precedent.

### Edge cases & constraints

Bare repo (Cherry-pick disabled with an explicit reason, per FR-115); unborn HEAD (disabled, per FR-115 — there is no `HEAD` to advance); detached HEAD (works normally, advances the detached `HEAD` directly, no special gate); worktrees (operation state is per-worktree per the already-shipped FR-76 — a cherry-pick in progress in worktree A shows no banner in worktree B's tab); a cherry-pick — single or multi-commit — started from a separate terminal before GitHydra opened the repo (detected via the same generic `inProgressOperationDetail` read as any other operation; FR-105's `remainingAfterCurrent` design deliberately requires no memory of the original request, so this case needs no special handling); a commit that's already an ancestor of current `HEAD` (falls through the same FR-105/FR-118 empty-result path as any other no-op result — no separate ancestry pre-check, see Non-goals); a submodule gitlink touched by a cherry-picked commit (an ordinary file change to this feature — any conflict it produces already gets the existing gitlink treatment from `merge-rebase-conflict-resolution.md` FR-77).

### A sharp edge worth stating plainly

Unlike rebase, which writes an `end` file at start recording its total step count (so `RebaseOperationDetail.totalSteps` survives even a GitHydra restart mid-rebase), git's multi-commit cherry-pick sequencer records *only* what's left in `.git/sequencer/todo` — it never persists the originally-requested total anywhere on disk. This spec deliberately does not fabricate one client-side (remembering "5 commits were requested" in memory would violate this codebase's "no authoritative in-memory state, git's on-disk state is the state" rule the same way a synthesized stash-abort would have) and does not silently drop the readout either. Instead, FR-105/FR-117 show "X more queued" — real, disk-truth information — rather than a "step N of M" framing that would be wrong or unknowable the moment GitHydra didn't start the sequence itself (or restarted mid-sequence). This is a deliberately less complete readout than rebase's, not an oversight.

## Non-goals (v1)

- **Cherry-picking a merge commit** (git's `-m <parent-number>` mainline-selection flag). A real capability, but it requires asking the user which parent is "mainline" — a meaningfully different, larger UI surface than anything this spec needs otherwise. Selection containing a merge commit is disabled with a reason (FR-115); deferred as a fast-follow, not dropped.
- **`git cherry-pick -x`** (append a "(cherry picked from commit ...)" trailer). Not exposed as a toggle — matches git's own default (off), avoiding a configuration surface for a preference most users won't need to change per-operation. Fast-follow candidate.
- **`git cherry-pick -e` / per-commit message editing before it's created**, and any interactive message customization mid-sequence. Matches FR-70's established precedent exactly (accept git's default message; a customize-message step, if ever built, is a follow-up amend using the existing commit composer, never an editor handoff).
- **Cherry-picking a commit that exists only on a not-yet-fetched remote ref.** The commit graph only ever shows locally-known history (no network calls anywhere, per every prior spec); this spec's selection surface is that same graph, so this case cannot arise without a separate `git fetch` happening first.
- **A proactive ancestry pre-check** that disables cherry-pick for a commit already reachable from `HEAD`. Left entirely to git's own empty-result detection (FR-105/FR-118) rather than a duplicated, potentially slow `merge-base --is-ancestor` check per selected commit — consistent with this codebase's "git's on-disk state is the source of truth, don't speculatively re-derive it" convention.
- **Drag-and-drop cherry-pick** (dragging a commit row onto a branch chip). A real GitKraken-style affordance, but a separate interaction surface layered on top of this spec's context-menu action — not required for a usable v1. Fast-follow candidate.
- **Any network call**, and **telemetry on cherry-pick usage, frequency, or conflict/empty-result rate.** None, per product principles — identical behavior across GitHub/GitLab/Bitbucket/self-hosted/local-only remotes.

## Acceptance criteria

1. Cherry-picking a single clean commit from the context menu creates exactly one new commit on the current branch whose diff matches the source commit's, with `HEAD` becoming that new commit.
2. Cherry-picking a 3-commit multi-selection with no conflicts creates exactly 3 new commits in oldest-first order regardless of click order, verified via `git log --oneline -3` matching the source commits' diffs in that order.
3. A cherry-pick attempted while another merge/rebase/cherry-pick/revert is already in progress is refused before any new git call is made (verified: no new `CHERRY_PICK_HEAD`/index state beyond the pre-existing operation), with the context-menu item shown disabled and an explicit reason.
4. A single-commit cherry-pick that conflicts shows the existing operation banner with cherry-pick-specific copy naming the commit's SHA/subject, populates `ChangesPanel`'s Conflicted section, and opens the same `ConflictResolutionView` merge/rebase conflicts use.
5. In a 5-commit sequence where commit 3 conflicts: commits 1-2 already exist in `git log` when the pause happens; the banner shows "2 more queued" matching `.git/sequencer/todo`'s actual remaining-line count; resolving commit 3 and clicking Continue completes it and pauses again only if commit 4 or 5 also conflicts; a final Continue leaves exactly 5 new commits in `git log` and `inProgressOperation` back to `null`.
6. Clicking Abort at any paused step of a multi-commit sequence restores `HEAD` to the exact SHA it was at before the sequence began (`git rev-parse HEAD`) — not merely undoing the current step.
7. Cherry-picking a commit whose changes are already fully present in the current branch pauses with the FR-118 empty-result notice (not `ConflictResolutionView` — `conflicted` is empty), offering Skip and Commit-empty; Skip advances the sequence (or ends the operation if it was the last commit) with no new commit for that step; Commit-empty creates an empty commit carrying the original message verbatim.
8. A 3-commit sequence with an empty-result step in the middle completes correctly end-to-end regardless of whether Skip or Commit-empty was chosen at that step, leaving `git log` with 2 or 3 new commits respectively.
9. Selecting a merge commit (alone, or within a larger multi-selection) shows Cherry-pick disabled with an explicit reason; no git call is made if clicked regardless.
10. On a bare repository and on a zero-commit (unborn HEAD) repository, Cherry-pick is disabled with an explicit reason.
11. Cherry-picking onto a detached HEAD succeeds and advances it directly, with no special gate or warning dialog.
12. Opening a repo where a multi-commit cherry-pick was started and paused from a separate terminal before GitHydra opened it shows the correct operation banner and FR-105 remaining-queued count matching disk state, and both Continue and Abort work correctly — with zero reliance on GitHydra having any memory of the original request.
13. Running `git cherry-pick --continue` from a separate terminal while GitHydra is open and idle on a paused multi-commit sequence shows a distinct alert (per `graph-head-indicator-and-refresh-alerting.md`'s Problem 2 policy) naming the operation and prompting the user to refresh; the banner's remaining-queued count does not update, and conflict-resolution actions (Continue, Abort, Accept Ours/Theirs, Mark as resolved) remain disabled, until the user clicks Refresh, at which point the count matches the current on-disk sequencer state.
14. None of a successful cherry-pick/skip/commit-empty/continue/abort ever shows the "History changed outside GitHydra" staleness banner as a result of its own action.
15. Zero outbound network requests occur across single-commit, multi-commit-clean, multi-commit-conflict, and multi-commit-empty-result flows, on repos configured against GitHub, GitLab, Bitbucket, a self-hosted remote, and a purely local repo with no remote.
16. After every successful step (clean apply, skip, commit-empty, continue, abort), the commit graph, `ChangesPanel`, and Toolbar working-dir badges reflect the result with no restart or manual refresh required.
17. Multi-selecting commits via ctrl/shift+click never changes existing plain-click behavior — a plain click after a multi-selection clears it and opens that single commit's `DetailPanel` exactly as before this spec.
